# 以案例库为核心的写作与返工

## 1. 先判断哪里出了问题

用户说“这里不对”时，读取被指出的内容及相邻段落；说“整篇感觉不对”时，先通读摘要、绪论、大纲、主要图组与结尾，再定位正文。不要一听到不满意就重写全文，也不要把整体问题当成几个用词问题。

结合实际稿件提出最可能的问题判断，用户的描述是诊断入口，不自动等于唯一原因：

| 层面 | 检查什么 | 优先检索词 |
| --- | --- | --- |
| 全文思路 | 中心问题是否明确，各节是否共同推进，结尾是否回应开头 | 主线、完整故事、整体感觉、文类错位 |
| 论证连接 | 选择是否有理由，结果是否得到解释，上下文关系是否讲清 | 研究者视角、章节衔接、结果解释 |
| 局部理解 | 对象、概念和作用是否交代，是否直接跳到细节 | 方法引入、选择依据、统计单位 |
| 阅读负担 | 是否把术语、数据和判断压在一起，让读者自己翻译和拼结论 | 信息密度、术语堆积、理解负担 |
| 交付错位 | 用户要方案或正式大纲，是否只收到分析、讲解或聊天标题 | 方案缺位、文类错位、过度口语化 |
| 语气与价值 | 是否像说明书，是否过度自评或谨慎，重要性是否写出来 | 自我评价、防御性写作、背景价值、贡献定位 |
| 图组叙事 | 是否只堆图，主线能否从图中读懂，视觉设计是否到位 | 中间过程、图组主线、高级感、真实图源 |

这些是检索入口，不是封闭分类。若同时存在几种问题，先处理决定文章走向的主线和论证，再调整局部语言。

## 2. 查找类似情形，读用户当时怎么评价

先看[实例索引](../实例库/索引-错误与提示词-v1.md)，再用管理脚本`list --query`搜索基础与成长库。查的是相似写作问题，而非同一个算法名；换用近义词，必要时列出全部有效案例。通常精读最相关的少量案例，不把整库复制成要求清单。索引中的“重要但未解决示例”单独用`list --unresolved`检索；它们只说明尚未解决的感觉，不能提供已经奏效的修法。

每条案例重点读取：当时哪里让用户不满意、旧稿及上下文、用户原始提示词和评价、修改采取了什么动作、用户是否认可，以及哪些条件与当前任务相同或不同。基础库说明用户确实指出过的问题；成长库中的反馈说明某一具体版本获得过认可。不能只读AI诊断而跳过用户原话。

**对“感觉不对”的返工，先向用户呈现诊断与历史原话，等待确认。** 用日常语言说明最可能的感受类型，例如“信息全有，但需要你自己翻译术语、拼出结论”，或“读得懂了，却不像可以直接使用的正式方案”。结合当前稿的具体位置解释判断；诊断仍是待确认的推测。

列出若干高度相关的历史提示词，通常2—4条；实际只有1条就只列1条，没有就明确说未找到。每条包含案例ID与链接、用户原话、与当前问题相似在哪里、当时改稿是否得到认可。长原话可摘取连续片段并标注节选，附完整记录入口，不把AI概括冒充原话。一次未满意的返工链必须标为反例，不能推荐模仿其中的AI回复。

最后请用户确认是哪种感觉、是否按建议方向修改。使用可用的用户输入工具或在最终回复中提出确认，随后等待；确认前可以阅读材料和检索案例，不改正文、不生成替换成稿。不能把沉默、时间经过或预选选项当作确认。此次确认来自用户对本技能的明确流程要求，不是通用审批。

用户已明确给出具体替换或修改指令、无需推测感受时，直接执行；同一轮已确认的方向不重复询问。没有相似案例时仍先说明当前判断并等待确认，不虚构匹配。本次方向确认只允许开始返工，不等于用户满意改稿，不能据此晋升成长库。

## 3. 将案例中的经验用于当前稿件

迁移的是修订思路：例如补齐某个理解断点、重排章节职责、解释结果的含义、让图组承载主线。不能把案例中的数字、算法、句式或认可范围直接搬过来。

方向确认后，整体不对时先恢复中心问题与推进顺序，必要时重构大纲，再改受影响段落和图组。局部不对时修复该处及真正同类的问题，检查上下文，不重写已有正确内容。新写作也先用主线组织材料，再参考最相关的历史案例避免已知问题。

需要补证据时，先查现有材料及任务允许的来源；不能用流畅措辞填补不存在的事实。只改写法不自动重跑模型或扩展实验范围。

## 4. 提示词作为辅助

完成必要的方向确认后，直接交付修改成果，不强制先生成或展示一份完整提示词。用户要求可复用提示词、需要交接另一位写作者或复杂返工值得留存操作说明时，再生成完整提示词，写清目标、材料、用户原话、具体修订和验收条件。确认阶段展示的是检索到的历史用户提示词，不能用新生成的提示词代替。

记录中保存实际采用的修订指令即可，短的可为几句操作说明；若确实生成并使用了完整提示词，则保存原文。不能事后编一份提示词，声称它曾被执行。需要形式示例时看[提示词与改稿示例](示例-提示词与改稿-v1.md)，不把示例作为每次必经步骤。

## 5. 将本次反馈留给下一次

按[成长规则](规则-实例收录与成长-v1.md)保留用户原话、旧稿、诊断、关联案例、实际修订动作、改稿及版本，先进入待验证。用户明确满意后收入成长库；新的不满意作为下一轮反馈保留，不能抹去前面的失败。

案例库是主要积累载体，核心规则保持简洁。一次认可只支持该情境下的修法，不自动成为所有写作的硬性模板。
